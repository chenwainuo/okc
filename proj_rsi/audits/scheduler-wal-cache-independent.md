Authoritative-prefix argument: a cache hit requires a valid local HMAC, exact metadata schema/version/ranges, SHA256 of EVERY currently read prefix byte, exact last-record bytes/hash/newline bounds and the original payload checksum/sequence/snapshot-envelope checks on that actual WAL record. State is reconstructed from that real WAL snapshot, never from checkpoint, cache-supplied state or a mutable previously returned Python snapshot. All appended records are strictly replayed. HMAC attests prior full validation of unchanged bytes; collision resistance and trusted signing code/key are assumptions. A changed prefix causes full strict replay, including same-length historical checksum/envelope corruption. Complete invalid records are refused, never truncated. Checkpoint contents cannot advance authority.

Missing/malformed/oversized/deep cache data, missing/bad key, bad seals, stale/misbound ranges and last records fall back to full replay. Prefix hashing is still O(total WAL bytes); this reduces repeated JSON/checksum work, not WAL I/O or disk growth. A future validation-rule change MUST invalidate/bump cache version rather than reuse old attestations. Rollback to old code ignores cache/key. Independently editing valid event payloads and recalculating unkeyed WAL checksums retains the original loader's semantics; neither loader authenticates operator intent or history against a malicious owner.

Recovery ordering remains the original policy. An incomplete final record is content-hash quarantined with atomic/fsynced evidence before truncating only that tail; then all complete records are validated. Complete historical corruption is still surfaced even if a torn tail was also present. This refactors existing recovery, not a new compaction/truncation policy. Crash after WAL fsync but before checkpoint/cache replays the tail. Checkpoint failures retain original behavior. New cache/key publication is best effort; optional write failures cannot suppress a durable WAL commit. Own commits extend only a verified prefix at matching size/sequence and revalidate the new record envelope before attestation. Orphan temporary files are ignored. Fsync/rename durability relies on the same POSIX filesystem assumptions as baseline; tests inject faults, not actual power loss.

Races/coexistence: every public operation still holds exclusive flock on the stable .lock inode for replay/append/publication. Old workers use the same lock/event format, ignore optional files and can append tails that new workers strictly validate. Old long-lived workers remain slow until their normal restart. No lease expiry becomes process death, no worker is killed, no active state is auto-released and no GPU ownership changes. Advisory locks do not protect against uncooperative manual writes; this proposal adds no such guarantee.

Key/permission limitation is explicit. New keys are atomically created as32 random bytes with fchmod0600 before publication. Existing32-byte keys are accepted without mode/owner/regular-file/symlink enforcement. My independent probe confirms a chmod0644 existing key remains accepted. The cache seal therefore is NOT a new hostile-user security boundary. Deployment must keep the queue directory, key/cache and their writable ancestry under trusted controller/operator control, with no untrusted directory writers or key readers. Read-only stat of current local directory shows775 ubuntu:ubuntu, WAL/lock664; trusting the ubuntu group is an operational assumption, not code-enforced isolation. If deployment requires resisting other directory writers or accepting arbitrary preexisting key paths, HOLD that broader deployment and add independently reviewed ownership/mode/O_NOFOLLOW checks first. Same-owner processes already can rewrite valid unkeyed WAL, so this does not worsen the expressly stated trusted-owner model.
