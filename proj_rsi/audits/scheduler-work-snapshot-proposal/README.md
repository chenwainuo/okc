# Isolated worker rank-read proposal

This proposal removes repeated full-WAL reads from `GPUDispatcher.work` without changing the live dispatcher or store. `QueueStore.rank(resource)` holds its lock for one WAL read and returns complete deep-copied job dictionaries, including state and launch bounds. Work can filter READY and inspect the reservation bound from those dictionaries. It need not call `get()` for each row and once again for the selected row.

The patch changes only that filter and candidate assignment, plus an explanatory comment. The existing preliminary running-ownership snapshot and rank read remain: two advisory reads per idle selection loop, rather than N+3 reads. No store method, WAL format, lock, mutation or claim behavior changes. Snapshot and rank are different moments; READY is only a hint. The unchanged `launch_next` calls authoritative atomic `claim`, which rebalances, ranks and checks current active capacity and ownership. Its existing deadline gate verifies the actually claimed job before requesting launch. Stale rank can still yield NO_CLAIM or a safely held reservation; this proposal does not create a retry or override admission.

`dispatch.py` is an isolated full proposal copy and `dispatch.patch` is the minimal reviewable diff. `baseline.json` pins live dispatch/store and the proposal. These are review artifacts, not the active implementation. Root must stop/reconcile the active controller and independently review/apply a new pinned dispatcher version before restarting; this author made no live worker/process/queue/GPU/SSH change. The patch must not be applied while an active worker is running.

Focused tests compare the original and proposed actual work functions using 1,000 full ranked rows. Original performs 1,001 get calls; proposed performs zero. This is a read-count proof, not a production WAL-time benchmark. Additional tests distinguish old snapshot state from current rank state; reject old READY when rank says HELD; keep atomic claim as the final authority; simulate a separate controller claiming between rank and claim on a temporary real QueueStore; and register a new higher-ROI 300-second job after a stale 60-second rank, showing the actual claim's deadline check holds it without any transport launch. The inherited dispatcher regression suite also runs against the proposal class. Total38 tests PASS, all CPU-only with fake transports and temporary queues.

The current live WAL size and observed controller slowness are root observations; tests do not load, copy, rewrite or compact the production WAL. This change makes advisory selection reads constant in job count; it does not solve the remaining per-operation full-WAL cost or checkpoint growth. Those would require a distinct reviewed store design. No end-to-end latency or GPU utilization improvement is claimed from the CPU tests.

Reproduce: `PYTHONPATH=. python3 proj_rsi/audits/scheduler-work-snapshot-proposal/test_proposal.py -q`.
