# P4b: how much per-stage ALU work one consumer warpgroup absorbs (decode slack), H100 box

**Kernels.** pw24h's bf16 pipelines with no cluster:
- **k2x:** 64×64 tile, BLOCK_K 128 (7 slots), pooler m=128, 128 CTAs.
- **n128x:** 64×128 tile, BLOCK_K 64 (9 slots), pooler m=256, 128 CTAs.

**Synthetic decode.** N `mad.lo.u32` per thread per k64 stage, sitting where the decode would.
- The four chains are seeded by an `ld.shared` of the landed W slot after the full-barrier wait.
- Their result feeds the stage's wgmma descriptor through an unprovable zero.
- SASS confirms the order TRYWAIT → LDS → N×IMAD → HGMMA.
- Earlier builds without the seed or the dependence were invalid: ptxas hoisted the chain above the wait or sank it below the HGMMAs, hiding it.

IMAD issues at 2 clk per warp instruction, the same as the LOP3/IADD3/SHF/PRMT a decode uses.

**Code and logs.**
- Code: `proj_rsi/candidates/pw24h/submission.py` (template parameter ALU) and `slack.py`, generated by `tools/mkslack.py`.
- Logs: `/root/okc/logs/pw24h-slack.log` and `pw24h-slack2.log`.
- Times are in-prepare µs (replay overhead ~3.5 µs). Stage period in clk = (t − 3.5) / 128 × 1980.

## Second math warpgroup (ping-pong; each warpgroup absorbs N on the stages it owns)

| N | 0 | 32 | 48 | 64 | 96 | 128 |
|---|---|---|---|---|---|---|
| pp, wait_group 1, k2, 7 slots (holds 2 slot periods) | 29.82 | 30.98 | 32.16 | 34.53 | 39.07 | 43.58 |

| pp, release after own wgmma, k1, 12 slots | 28.83 | 32.54 | 34.72 | 36.99 | 41.28 | 42.94 |
| pp, release after own wgmma, 64×128, m=256 | 34.30 | 40.38 | 42.08 | 43.78 | 48.45 | 52.90 |

The second math warpgroup never helps; it is worse than the single consumer at every N. Past the knee the limit is INT issue throughput per SM sub-partition: each k64 stage's N ops run on one warp per sub-partition at 2 clk each, whichever warpgroup owns the stage. It is not one warpgroup's latency, so a second math warpgroup only adds its own overhead. A separate transform warpgroup has the same problem: it shares the same issue slots.

## Reading

**k2x (64×64, m=128).**
- Slack is about 48 ops per thread per k64 stage on the H100: +0.4 at 16, +0.7 at 32, +1.0 at 48, then +3.3 at 64.
- Past the knee the slope is 2.2 clk per op per stage (0.14 µs per op over 128 stages).
- Fit: consumer service time S(N) ≈ 286 + 2.23·N clk per k64.
- Stream period on the H100 is ≈ 365–379 clk, so the knee is at N ≈ 40–50.

**n128x (64×128, m=256).** It has no slack: +4.6 µs at only 16 ops. Its consumer is already near-bound with 2× the tensor work per stage, and the decode per stage is the same W work.

**H200 scaling (0.7× stream period, ≈ 255–265 clk per k64; clocks equal).**
- S(0) ≈ 286 clk already exceeds the period. The single consumer is at or past the knee with no decode at all; the judge transfer test of pw32's k2x path confirms or refutes this directly.
- Each decode instruction then adds about 2.2 clk per stage: 36–50 instructions ≈ +80–110 clk per stage ≈ **+5–7 µs** at pooler m=128 on the judge.
- On the H100 the same 36–50 instructions cost about +0.6–1.1 µs.

**Answer for the 12-bit builds.**
- On the H100, pw10's dec1 cost (36–50 instructions per thread per k64 at 64 rows) just fits one consumer.
- On the H200 it does not fit, and a second math warpgroup does not fix it, because issue throughput is shared.
- What would fit:
  - fewer decode instructions per weight: about ≤ 16 per thread per k64 (+0.4 on the H100), e.g. packed-pair PRMT tricks; or
  - a geometry with more stream time per decoded weight.
- At m=256 neither 64×128 tile variant has slack for any decode.

## Software-pipelined placement (coordinator's rung), runs slack3 / slack4

**What these rungs do.** Stage s+1's slot is waited and read with 3 `LDS.128` per thread per k64 (6 KB per k64 per CTA, the 12-bit payload). N ops then run on that data. The result feeds stage s+1's W descriptor. All of this happens after stage s's wgmma commit, so it overlaps wgmma(s).

**Two orders:**
- **(q) decode-first, as specified:** commit(s) → wait(s+1) → LDS → ops → wait_group(1) → release(s−1).
- **(r) release-first:** commit(s) → wait_group(1) → release(s−1) → wait(s+1) → LDS → ops.

**Chain shapes.** "4 ch" is four independent chains of N/4 (ILP); "1 ch" is one dependent chain of N. The critical-path "d" curve above is likewise N ops in total over four chains.

**Build fixes needed first.** A branch in the loop body put ptxas's injected warpgroup.arrive on a divergent path and serialized the wgmma (C7520). The first and last stages are peeled, and the SASS order was checked: HGMMA(s) → DEPBAR → release → TRYWAIT(s+1) → LDS.128 → IMAD → HGMMA(s+1).

**Reading.**

1. **Pipelining buys no slack on this pipeline.**
   - Past the first 16 ops, every placement has the same slope: about 2.1–2.2 clk per op per k64 stage (k2x release-first: +10.9 µs from 16 to 96 ops).
   - That is the per-warp INT issue rate (IMAD, LOP3, PRMT and SHF all issue at 2 clk per warp instruction on H100), not a dependency latency.
   - Overlapping with the async wgmma cannot hide issue slots the consumer warp itself must spend.
2. **One dependent chain is much worse** (latency-bound). A decode needs at least 4 independent chains per thread.
3. **Reading slot s+1 (N=0) costs +0.85 µs at k2x and +5 µs at n128x by itself.**
   - These SS kernels already move 32 KB (k2x) or 48 KB (n128x) of TMA writes plus wgmma reads per k64. The extra 6 KB of LDS pushes n128x over the 128 B/clk smem port (≈ 55 KB per 433-clk stage).
   - This part is pessimistic for a real RS 12-bit kernel. There A comes from registers (no 8 KB wgmma A read) and W lands as 6 KB, not 8 KB. A real decode's reads replace the A read, not add to it.
4. **For the 12-bit builds** (36–50 decode instructions per thread per k64 at 64 rows):
   - Expect about +2.2 clk per instruction per stage beyond roughly 16–48 instructions of slack on the H100: ≈ +0.6–1.1 µs at pooler m=128 on the box.
   - Expect about +5–7 µs on the H200, where S(0) ≥ the stream period.
   - Software pipelining, ping-pong or a transform warpgroup do not change this; the fix is fewer instructions per weight.
