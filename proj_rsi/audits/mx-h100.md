# mx: two-plane 12-bit RS-wgmma CUTLASS GEMM on the H100 box (M1–M3)

Code: `proj_rsi/tools/plane_pack.py` (packer, decoder, proofs), `proj_rsi/candidates/mx/mx_mainloop.hpp` (forked sm90
mixed-input mainloop), `proj_rsi/candidates/mx/mx_kernel.hpp` (forked KernelTmaWarpSpecialized operator(): K-split grid.z,
2 math warpgroups, reduce-add epilogue, in-kernel zeroing), `proj_rsi/tools/mx_bench.py` (build / validate / time; read
flush like the bake). Raw logs on the box: `/root/okc/logs/mx_m3.txt`. All µs below are box graph-replay µs and include
about 3.7 µs of replay overhead.

## Format

- r6's code (8-code h7 window, dec1, 9 int ops per 8 weights), packed directly in wgmma m64k16 register-A fragment order.
- Each (64-row unit, k64 tile) is one 6208 B chunk:
  - 4096 B plane8;
  - 2048 B plane4;
  - a 64 B escape header: count, then up to 15 entries of (row, k, xor16).
- Bytes: 50.9 MB vs 67.1 MB bf16.
- Escapes are about 1.4e-4 of the weights, all tiny (the window contains the max).
  - The consumer XORs the true bf16 bits into the decoded fragment register, so the A operand is exactly W.
  - Outputs are bit-identical to `x @ W^T` at S = 1.
- Lossless, verified on all four layers (cuda reference weights) through both the escape list and the headers.

## Findings

1. **Not x-traffic bound at m=128, but stage-depth bound plus a consumer loop near tensor throughput.**
   - Probes on ws 64x64 c1x2, pooler: no B loads −0.8 µs; no A loads −1 µs; no decode −4 µs (stock per-k-block schedule).
   - On ws 64x128 S2:
     - stages s4 / s6 / s9: 36.8 / 27.5 / 25.3;
     - no A loads 21.0, no B loads 24.7, no decode 25.3 (no change).
   - The pure consumer loop (no loads at all) is 17.0 µs (no decode) and 19.7 µs (with dec1) for pooler. It is RS m64n128k16 at about 62% of nominal peak. The full kernel is 25.7.
   - A deeper separate A ring at the cost of B stages (s4 + a20) is much worse (43.9): B depth matters as much.
   - 128-row cooperative tiles with split-K (RS128 geometry) are **not** faster than 64x128 S2 at e0 (26.1 vs 25.8).
2. **The CUTLASS TMA epilogue issues each store from a whole warp (32 identical bulk ops).**
   - Harmless for a plain store, 32x for a reduce-add.
   - `mx::OneLane` fixes it for the K-split reduce-add epilogue.
3. **Split-K with in-kernel zeroing.**
   - The memset node cost about 1.5–2 µs.
   - Now split 0's three idle producer warps zero the tile at entry and publish a flag. Every split's epilogue acquires it, the last one resets it, and it is self-cleaning.
   - Net cost is about 0.
4. **Escapes: every mechanism on the consumer's path costs µs, because the single math warpgroup has no slack.**
   - Prologue gathers: +32 µs.
   - Aux-warp gather plus a post-loop apply: +5–9 µs. A scattered L2 gather under a saturated stream takes 15–18 µs.
   - x copied from the B stage: +5 µs.
   - Fragment XOR patch: +3.5 µs (one math WG) and **+0.45 µs with two math warpgroups**.
   - Lossy (no correction) passes the checker at rel 3e-6, but is not lossless.
5. **Two wgmma groups in flight** (3 A buffers, wait<2>): −0.5 µs.

## Transferable lessons (for RS128 and any register-A packed GEMM)

### 1. Escapes: XOR patch from a 64 B header per (64-row unit, k64) chunk

**Header layout.** The header sits at the end of each 6208 B chunk and travels in the same bulk copy as the planes, so it adds no global access and no latency:
- `u32 n`;
- then up to 15 × `u32` entries, each `row << 22 | (k % 64) << 16 | (w ^ w_dec)`.

The overflow check is done at pack time. Max per chunk on the reference weights is well under 15; pooler averages 0.55 per chunk.

**Consumer procedure.**
- `n` is loaded with the plane LDS.128s, as one extra `ld.shared.u32` issued before the decode.
- After `decode_all`, when `n != 0`, each entry is read.
- The owner of (r, kk) in the m64k16 RS fragment is thread `32 (r / 16) + 4 (r % 8) + (kk % 8) / 2`.
  - Its k-block is `kk / 16`.
  - Its register is `(r / 8) % 2 + 2 ((kk / 8) % 2)`.
  - Its half is `kk % 2`.
- The owner XORs `xor16 << 16·half` into that register. This is a static 16-way predicated XOR, because registers cannot be indexed dynamically.

**Result.** The A operand is exactly W, so there is no fp32 correction, no apply pass and no smem. At S = 1 the output is bit-identical to the reference.

**Cost.** Pooler m=128 costs +3.5 µs with one math warpgroup and **+0.45 µs with two** (co128x128).
- The single-WG consumer has no slack in the decode shadow (see 4), so any per-stage serial work lands on the critical path.

**What failed, so it need not be retried.**

| Mechanism | Cost |
|---|---|
| Escape prologue with global gathers of x[:, k] | +32 µs |
| Aux-warp global gather plus a post-loop smem apply | +5–9 µs; the scattered gather took 15–18 µs under the saturated stream |
| x[:, k] copied from the resident B stage by the consumer | +5 µs |
| Same with a mid-loop apply | worse |

Dropping the correction entirely ("lossy") passes the checker at rel 3e-6, but is not lossless.

### 2. Self-cleaning split-K zeroing

The output is reduce-added (TMA `cp.reduce.async.bulk .add`, bf16), with no memset node. The memset node measured 1.5–2 µs on the box.

**At kernel entry (producer warpgroup).** Split 0's three idle producer warps:
- zero the tile's out region with `st.global.v4`;
- `__threadfence()`, then `bar.sync` among the 3 warps;
- `st.release.gpu` `flags[2 tile] = 1`.

**Before the epilogue (consumer warpgroup), every split including 0:**
1. Thread 0 spins on `ld.acquire.gpu flags[2 tile]`.
2. It does `atomicAdd(&flags[2 tile + 1], 1)`. The last of the S waiters resets both words to 0. The next launch is stream-ordered, so the reset is safe.
3. `bar.sync` among the consumer threads.
4. `fence.proxy.async.global` before the TMA reduce.

**Cost.** About 0: the zeroing finishes in under 5 µs of a 20 µs mainloop and the flag is never waited on.

**Requirement.** The flags must be zero-initialised once, in a persistent workspace. One-hot rows stay exact because the other splits add exact zeros.

### 3. The reduce-add store-lane fix

CUTLASS 3.9.2's TMA epilogue predicates the store with `issue_tma_store = (thread_idx / 32) == 0`, so all 32 lanes of warp 0 issue the bulk op.
- For a plain store this is idempotent and costs nothing measurable (plain stores at one lane are no faster).
- For a reduce-add it adds 32×: rel error 31, plus about 25 µs of atomics.

`mx::OneLane<Op>`, a `Copy_Traits` specialisation in `mx_kernel.hpp`, issues from lane 0 only. Any hand epilogue must likewise issue from one elected thread.

### 4. What bounds the m=128 mainloop (ws 64x128, pooler S2, 64 k-tiles per CTA)

**Stage count.**

| Stages | µs |
|---|---|
| s4 | 36.8 |
| s6 | 27.5 |
| s9 | 25.3 |

The kernel is bytes-in-flight bound: at about 300 ns per stage and 22.5 KB per stage, 9 stages cover about 2.7 µs of HBM/L2 latency under load.

**Probes (all one-variable).**

| Probe | µs | Δ vs 25.3 baseline |
|---|---|---|
| No B (x) loads | 24.7 | −0.6 |
| No A (W) loads | 21.0 | −4.3 |
| No decode | 25.3 | 0 |
| No loads, no decode (pure RS wgmma loop) | 17.0 | |
| No loads, with dec1 | 19.7 | |

The pure RS wgmma loop is 13.3 µs of kernel for 4 × m64n128k16 per stage, about 62% of the nominal dense peak.

**Interpretation.**
- The W stream's latency is what binds, not x L2 traffic and not the decode.
- But any serial work added to the consumer between the wait and the next issue (escape handling, extra LDS round trips) costs about 1:1. The decode itself fits in the shadow of one wgmma group, and barely.
- Two groups in flight (3 A buffers, `wait<2>`) gain 0.5 µs.

**Separate, deeper W ring (own mbarriers, released right after the LDS).** This was tried at the price of the x ring: s4+a20 gave 43.9 and s3+a24 gave 57.8. The x ring needs depth too, so a W-only deeper ring only helps if the x ring keeps about 9 × 16 KB.

### 5. m=256 is compute-bound on the H100

The best RS configs are 32–37 µs against 29.7 (r6) and 31.2 (bf16 CUTLASS, non-swapped 64x128). RS m64n128 runs at about 62% of peak, below cuBLAS's SS kernels. Do not serve m=256 from an RS-decode kernel on this evidence.

### 6. Stamps (globaltimer, median over CTAs, from the first CTA's start, pooler ws 64x128 S2)

| Event | µs |
|---|---|
| Consumer start | 0 |
| First wgmma | 1.5 |
| Mainloop done | 18.7 |
| Epilogue done (reduce-add + flag) | 20.2 |

So the epilogue tail is about 1.5 µs and the time to the first wgmma about 1.5 µs. These are fixed costs that carry 1:1 to the H200.

## mx vs RS128 (rs128 R2 `7700384`, LOOP.md "RS128 R2")

Both designs share the same geometry family: swap-AB; register-A dec1 decode; x as K-major SW128 smem B; split-K with an in-kernel-zeroed bf16 TMA reduce-add.

| Per-CTA term (pooler m=128) | mx (CUTLASS fork) | RS128 R2 (hand) |
|---|---|---|
| Tile and split | ws 64x128 S2 (64 k64 stages of 6 KB W), or co 128x128 S4 (32 stages of 12 KB) | 128x128 KS4 (32 stages of 12 KB), WM0, ST5 |
| Ring | 9 (ws) or 7 (co) stages; one full barrier for W+x; one CUTLASS empty barrier, released after the wgmma wait | 5 slots; one full barrier for W+x; **separate W empty (released at the LDS) and x empty (after the wait_group)** |
| L2 policy | none | **W evict_first, x evict_last (−1.2 µs)** |
| Entry to first wgmma | 1.5 µs (ws) | 2.0 µs |
| Last wgmma to exit | 1.5 µs (CUTLASS TMA epilogue + flag acquire) | 1.5 µs (0.8 of it the `wait_group.read` on the slab) |
| Stage period | ~0.30 µs per 6 KB (ws) / ~0.60 µs per 12 KB (co); kernel 22.0 / 22.4 µs | **~0.44 µs per 12 KB**; kernel 21.86 |
| Escapes | 64 B header inside each W chunk (n + 15 entries), read from smem with the planes | per-warp lists at a fixed stride, the first 32 entries loaded into registers before the W flood, shfl walk |
| Decode placement | MX_SCHED 2: 3 A buffers, wait<2>, −0.5 µs vs wait<1> | WM0 (decode on the wait-to-issue chain); WM2 measured +0.4 |
| Zeroing | split 0's 3 idle producer warps zero the whole tile, release flag, consumers acquire | each CTA zeroes 1/KS of the block, counter, flag polled by an idle producer warp |

### What mx should borrow from RS128

1. **L2 cache hints**: evict_first on the W bulk copies, evict_last on x. This was −1.2 µs for RS128.
2. **Early W release.** RS128 releases the W slot at the LDS rather than after the wgmma. My split A ring (own full and empty barriers) did this but sacrificed x depth. RS128 shows the release alone, at an equal slot count, is the useful part.

Together these probably explain most of the 0.6 vs 0.44 µs per 12 KB period gap. RS128 also shows that a ring depth of 5 beats 8 at KS4 (it evens the HBM share across CTAs). mx never tried fewer stages than 7 on co128.

### What RS128 can borrow from mx

1. **The escape header in the W chunk.**
   - It removes the escape-list global loads entirely: no ecap layout, no pre-flood load, no refill `__ldg` every 32 entries.
   - It costs 64 B per 6 KB (+1%).
   - It is the likely source of mx's 0.5 µs earlier first wgmma (1.5 vs 2.0).
   - For RS128's 12 KB 128-row chunk: one header per 64-row tile, or per warp (8 per chunk). The owner arithmetic is the same as `rq_fix`'s lane/reg/half.
2. **Triple-buffered A with wait_group 2 (decode under two queued groups).**
   - mx measured −0.5 µs with it, at 64-row/one-WG stages.
   - RS128's WM2 lost 0.4 at 128 rows. Probably INT-bound there (two WGs), so this one is shape-dependent. Re-measure only if the stage period drops below about 600 clk.
