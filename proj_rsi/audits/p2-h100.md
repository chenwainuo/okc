# P2 on the H100 box: qkv_gate at m <= 32 (pw28 / pw28h), 2026-10-26

Box: H100 80GB HBM3 (132 SMs), torch 2.8 / CUDA 12.8 container. Tool: `proj_rsi/candidates/pw28h/lab.py`.
- It compiles only the instances a plan needs.
- It validates every full-n path with the submission's `_validate`: one-hot x8 bit-exact, random rows, odd m.
- It times every variant interleaved round-robin. Each launch follows a read pass over 256 MB (cold L2).
- Times are **CUPTI kernel durations** (kineto), median of 60-80. There is no graph-replay overhead in them, so they are
  kernel-side µs on the H100 and not judge µs.
- Logs on the box: `/root/okc/logs/p2/{base,deep,lad32,lad1x}.log` and `.json`.

## 1. Ladder at m=1 (r6's m=1 pick `gv<1,1,2,1,8,16,1,1,0,1>`, 144 CTAs x 8 warps x 16 chunks)

The bare stream probe (`rd<U>`, grid-stride `ld.global.nc.L1::no_allocate.v4`, best over 5 grids and 3 depths) gives:
- 25.2 MB: **9.41** µs (2.67 TB/s)
- 28.3 MB (exactly qkv's 12-bit W): **10.43** µs (2.71 TB/s)
- 50.3 MB: 17.41 µs (2.89 TB/s)

So the H100's fixed cost is about 1 µs, and the marginal rate is about 3.2 TB/s.

| rung | grid 144 (real) | grid 132 (no tail) | grid 128 |
|---|---|---|---|
| W loads only, all hoisted (162 regs, 1 CTA/SM) | 11.49 (12 CTAs in a 2nd wave) | 9.95 | 9.63 |
| W loads only, regs <= 128 / <= 85 (minBlocks 2 / 3) | **10.75** / 10.82 | | |
| + x loads (162 regs) | 11.33 (2nd wave) | 10.08 | 9.79 |
| + decode + escape walk (72 regs) | 11.71 | 11.01 | 10.59 |
| + mma (106 regs) | 12.03 | 11.55 | 10.99 |
| full (reduce + epilogue) | **12.22** | 11.42 | 11.30 |

Reading:
1. **The tail is not the gap.** Cutting the grid from 144 to 132 CTAs saves 0.80 µs for 8.3% fewer bytes. A
   bandwidth-bound kernel would save 0.85 µs (8.3% of the ~10.2 µs stream part). Twelve SMs carrying a second tile
   overlap it: they hold twice the loads in flight and take twice the bandwidth share. That is why stream-K has
   nothing to win.
2. **W delivery is at the stream.** r6's own load pattern, alone and at its real occupancy, runs 10.75 against a
   bare 10.43 for the same bytes (+0.32).
3. **The excess is x, decode, mma and the epilogue.** 10.75 → 12.22 = +1.47 µs. The steps measured so far are
   +0.96 (x + decode + escapes), +0.32 (mma) and +0.19 (reduce/epilogue). Their register counts differ, so the
   split between x and decode is confounded. The clean ladder with every rung at minBlocks 2 is in section 1b.
4. Speed of light on this box for qkv m=1 = the bare stream of its 28.3 MB = 10.43. r6 is at 1.17x.

### 1b. Clean m=1 / m=8 ladder: every rung at r6's real occupancy (minBlocks 2, <= 128 regs; logs/p2/lad1x)

| rung | m=1, grid 144 | step | m=1, grid 132 | m=8, grid 144 | step |
|---|---|---|---|---|---|
| bare 28.3 MB stream | 10.43 | | | 10.43 | |
| W loads only | 10.69 | +0.26 | 9.95 | 10.72 | +0.29 |
| + x loads | 11.10 | +0.41 | 10.11 | 11.20 | +0.48 |
| + decode + escape walk | 11.55 | +0.45 | 10.75 | 11.94 | +0.74 |
| + mma | 11.97 | +0.42 | 11.17 | 12.06 | +0.12 |
| full (smem reduce + epilogue) | **12.35** | +0.38 | 11.71 | 12.48 | +0.42 |

The m=1 gap to the stream (+1.9) is four roughly equal per-chunk terms of about 0.4 each. No single one dominates.
More W depth does not move them (section 2), and neither does balance (section 0). Each term sits on the warp's
slot-recycle chain: a W slot is reloaded only after its chunk is decoded. The chain is longer than the
latency × depth product that the W-only rung tolerates.

### 1c. Ladder at m=32 (r6's H100 m=32 pick `gv<1,4,2,1,8,16,1,1,2,1>`, x loaded at use through L1, 2 CTAs/SM cap; logs/p2/lad32)

| rung | grid 144 (real) | grid 132 | grid 128 |
|---|---|---|---|
| W loads only | 10.75 | 9.97 | 9.63 |
| + x loads (32 tokens x 128 B per warp-chunk, 75 MB L2->SM) | 14.66 (**+3.91**) | 11.78 (+1.81) | 11.42 (+1.79) |
| + decode | 14.88 (+0.22) | 14.62 (+2.84) | 14.30 (+2.88) |
| + mma | 15.52 (+0.64) | 14.37 | 14.19 |
| full | **15.78** | 14.62 | 14.43 |

At m=32, x + decode together add 4.1-4.7 µs over W-only. The split between them depends on the grid (the x-only rung
is pathological at 144 CTAs), so treat x + decode as one block. mma adds about 0.6 and the epilogue about 0.3. The
m=32 excess over m=1 (+3.5) is this block: the x re-read (2.7x the W bytes through L2) on the per-chunk chain.

## 2. Deeper W rings (lever: depth instead of balance). All tie or lose.

stream-K 128 CTAs at 1 CTA/SM can afford a deep register ring with no second wave. Measured at m=1 (m=8 is the same
within 0.2):

| path | ST | regs / spill | m=1 | d vs r6 |
|---|---|---|---|---|
| gk 9 warps x 16 | 2 / 4 / 6 / 8 | 104 / 144 / 168 (104 B spill) / 168 (248 B) | 12.53 / **12.35** / 13.28 / 15.14 | +0.29 / +0.11 / +1.04 / +2.90 |
| gk 8 x 18 | 4 / 8 / 12 / 16 | 144 / 224 / 255 (144 B) / 255 (560 B) | 12.45 / 13.06 / 14.70 / 20.34 | +0.21 / +0.82 / ... |
| gk 18 x 8 | 3 / 4 | 96 (56 B) / 96 (168 B) | 12.82 / 15.38 | |

At m=16/32 (x through L1), the gk ST 2-8 and 8x18 variants run 15.4-18.6 at m=16 and 17.7-22.5 at m=32. That is
+1.8 to +6.7 over r6, and they get worse with depth. The register file, not the bytes in flight, is the binding
resource. A deeper ring does not reduce the +1.5 µs, which confirms that the excess is not latency starvation of the
W stream.

## 3. Attacks on the x term (m = 16 / 32)

**RT = 2: x reused from registers for two 16-row tiles.** It needs a cluster split-K S = 2 or 4 to keep 144 CTAs,
and the register cap is lifted (logs/p2/rt2). It loses everywhere:

| geometry (WK, KU, S, XS, ST, minB) | regs | m=16 | m=32 |
|---|---|---|---|
| r6 best (same run) | | 13.57 | 15.84 |
| 4, 16, 2, L1, 2, 2 | 170 / 226 | 14.95 | 16.80 |
| 4, 16, 2, regs, 2, 2 | 202 / 255 | 14.53 | 16.70 |
| 4, 8, 4, L1, 2, 2 | | 17.66 | 20.98 |
| 8, 8, 2, L1, 2, 1 (1 CTA/SM, 2nd wave) | | 18.64 | 21.68 |
| 2, 16, 4, L1, 3, 3 | 194 / 246 | 15.46 | 17.28 |

Halving x bytes does not pay for the cluster reduction, half the warps per CTA, and 200+ registers.

**WR = 2 without split-K: two row-tile warps of one CTA read the same x lines (L1 dedup).** 72 CTAs on 72 of the
132 SMs (logs/p2/wr2):

| geometry (WR, WK, KU, ST) | threads / regs | m=16 | m=32 |
|---|---|---|---|
| r6 best (same run) | | 13.60 | 15.87 |
| 2, 8, 16, 2 | 512 / 108-128 | 13.41 (-0.19) | 16.10 (+0.22) |

72 SMs at 32 warps each carry the whole stream. At m=16, one CTA of 2 row tiles x 16 K-warps with a 1-deep ring
beats r6's cluster-4 pick by 0.8 µs.

Reading:
- **What wins is per-warp chain length, not balance or depth.** KU 8 per warp with a 1-deep ring and 16 K-warps per
  tile beats r6's 8 warps x KU 16 x ST 2 by 0.4-0.6 at m=1/8. It also wins at 144 CTAs (2 CTAs/SM, 64 regs), so WR 2's
  72-SM layout is not required.
  This is consistent with section 1b. Each per-chunk term (x, decode, mma) lengthens a warp's slot-recycle chain.
  Twice the warps with half the chunks each halve the chain, while the bytes in flight per SM stay the same.
- 72 SMs at 32 warps each carry the full HBM stream (the WR 2 rows). Half the SMs idle costs nothing measurable here.
- At m=16, x sharing between the two row-tile warps adds to this. The cluster-4 split-K that r6 picks costs about
  1-1.4 µs against either geometry.
- **m=32 stays with r6.** Every short-chain geometry at MT 4 needs more than the 64 registers that 1024 threads (or
  2 x 512) allow. Splitting m=32 into two MT-2 token blocks re-streams W and costs +3.8. The register-free WR 2 x
  KU 16 (128 regs) only ties.

## 7. What transfers to the H200 judge, and what to ship

**Ship** these qkv_gate GVC entries (pw28h/submission.py; r6's bake chooses per run):
- MT 1 (m=1, 8): `((2, 16, 8, 1, 1, 2), (1,))` and `((1, 16, 8, 1, 1, 2, 1), (1 | 2 << 12,))`
- MT 2 (m=16): `((2, 8, 16, 1, 1, 0, 2), (1,))`, `((2, 16, 8, 1, 1, 2), (3,))` and `((1, 16, 8, 1, 1, 2, 1), (1 | 2 << 12,))`

Cost: five more gv instances (about +10 s compile on the judge). GK = False removes pw28's ten gvk instances and their
bake.

**Expected on the judge.** The mechanism is shorter per-warp slot-recycle chains, so the bytes in flight per SM are
unchanged. It should hold or grow on the H200: the stream is 1.4x faster there, so a fixed per-chunk chain cost is a
larger share of it.
- The 72-SM WR 2 variants need about 65 GB/s per SM on the H200, against about 39 GB/s here. That is within the L2->SM
  port but untested.
- The 144-CTA 16-warp variant (minBlocks 2) is the safer one on that count. Both are in the table and the bake decides.
- Rough judge estimate: if the H100 kernel deltas scale by the 0.7 HBM ratio, about -0.4 µs at m=1/8 and -0.8 to -1.0
  at m=16, which is about 15 x 0.4 x 2 + 11 x 0.9 ≈ 22 score-µs.

**Does not transfer / closed on real hardware:**
- stream-K balancing (pw28): the tail is overlapped by 2 CTAs/SM.
- Deeper W rings: register-bound, with spills.
- RT 2 x reuse with a cluster split.
- m=32 in two token blocks.
- WR 3 / WR 4 (36-48 CTAs).

8-row tiles were not built: section 1 shows tile granularity is not the limit.

**Open:** m=32 (15.7 vs m=1 12.2 here). Its x + decode block (+4.1) needs a short-chain geometry that fits MT 4 in
64 registers per thread. Two options: x fragments loaded per k16 step instead of per chunk, or MT 4 split across
the two row-tile warps. Both are code changes, not table entries.
